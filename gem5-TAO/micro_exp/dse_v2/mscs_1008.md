# MSCS 引导 DSE：尝试与结论（截至 2026-10-08）

核心问题：MSCS 的 16 维分量，能否在 DSE 中提供 scalar CPI 之外的信息，从而更快、更好地找到 Pareto 前沿。

所有结果均基于 surrogate（`exp1/results/lambda_sweep_1004/t10_c1_m0p01_s42.pt`），seed 42，HV 用公共参考点计算。

---

## 1. 完整 DSE 对比

| 实验 | 设定 | 结果 |
|---|---|---|
| v2（`results_v2_1005`） | 8 种方法，联合 17 个 benchmark | BO+refine 约等于 BO；greedy_mscs ≈ greedy_scalar，**两者在每个预算下都比 random 差**（5000 次 query 时 HV 0.90 vs 0.94；50 次时 0.61 vs 0.86） |
| v3 联合（`results_v3_1006`） | BO + 差分 refine（21 个参数，多尺度回收） | 相对 BO：scalar +1.04%，MSCS +0.44%；MSCS 只在 25–50 mm² 区间更好 |
| v3 单 benchmark（`results_v3_single_1006`） | 同上 | 有赢有输；关闭解耦的反事实：gcc 上解耦有害，xalancbmk 上关闭解耦反而更好 |
| v4 联合（`results_v4_1007/joint_17`） | 平台阈值改为相对值；解耦的增益下限 γ；保护参数可调 | τ_m=0.05：+0.74%；不加保护：+0.37%；仍只在 25–50 mm² 区间胜出 |
| v4 单 benchmark（12 个） | 同上 | 相对 BO 的平均 HV：v4 +2.08%，scalar +1.84%；v4 对 scalar 7 胜 2 平 3 负，差距 0.2–3%，在 surrogate 误差范围内 |

## 2. 机制诊断（v3/v4 中的保护与解耦）

| 诊断 | 问题 | 结论 |
|---|---|---|
| 日志分析（v4 walks） | 解耦有用吗 | 解耦占步数比例与 v4 优势负相关（Spearman −0.43）；解耦之后下一步的增益反而更低，没有帮助跳出平台 |
| `diag/protect_diag` | 保护拦下了什么 | τ_m=0.02 拦下 120 个可接受回收中的 56 个（26.8 mm² 中的 19.6 mm²） |
| `diag/reclaim_label` | ‖ΔMSCS‖₁ 能否预测"回收后会被加回" | scalar 实际执行的回收几乎从不被加回（118 次中 2 次）；在需要保护做判断的候选上，所有指标的 AUC 都在 0.50–0.58，‖ΔMSCS‖₁ 为 0.51 |

**结论**：v4 赢的地方更可能是因为它更保守，而不是因为单步决策更好。

## 3. MSCS 作为"该评估什么"的指引（`mscs_guide/`）

| 检验 | 问题 | 结果 |
|---|---|---|
| 映射（`build_map`） | 参数 → 压力分量的响应 | 不稀疏，也不完全符合物理直觉：缓解后端压力最多的是 fetchBufferSize；ROB 在任何分量上都不进前 3 |
| A1 剪枝 | 不评估就给 21 个增加方向排序 | MSCS 最好的版本前 5 名命中 0.60；对照"上一步实测"0.77、"面积最小先试"0.76 |
| A2 回收排序 | 少评估回收候选 | MSCS 只省约 1 个 query；**按省面积从大到小评估，第一个可接受的 100% 就是最优回收**（与 MSCS 无关） |
| B 组合移动 | 平台期推荐参数对 | 平台大多是假的：最好的参数对增益是最好单参数的 2–20 倍。mscs_cover 达到上限的 0.45，scalar 组合 0.39，随机 0.38；"第二瓶颈"规则失败 |
| 掩盖（`check_masking`） | 用压力**水平**区分"闲置"和"被掩盖" | 掩盖存在（最好参数对增益中位数是最好单参数的 4 倍，其中 33% 是配置约束导致）。AUC：压力水平 0.58，‖ΔMSCS‖₁ 0.43（反向）。60 个状态中 52 个最高压力类别都是后端（14 个参数），"类别内搜索"的效果（0.60）不如同等数量的随机参数对（0.74） |

## 4. 理论层面的检查

- **ArchExplorer 为什么能赢**：它每次评估直接读出按资源命名的瓶颈（ROB 满、IQ 满……），每步只需 1 次仿真。我们的 greedy 每步要做 25–40 次差分，MSCS 只是在差分结果上做修饰，没有节省 query；MSCS 的 FP/BP/SP 粒度也无法对应到具体参数。
- **Composite BO（Astudillo & Frazier 2019）**：结构上部分吻合，但 CPI = mean 1/(Base·W_min) **只依赖 Base 和 W_min**；FP/BP/SP 只通过 Base = 1 − ΣP 线性进入。g 的非线性部分只用 CPI 就能拿到（Base = 1/(CPI·W_min)），所以该理论不专门支持 MSCS 分量。
- **雅可比**：每步 1 次 query 替代 21 次，可以省很多 query，但 ∂CPI/∂θ 是 scalar 自身的信息。注意已知的求导盲点：只对 arch slot 求导，漏掉了随 config 变化的吞吐分布特征。

## 5. 总结

1. 只要 MSCS 被用来**替代或推翻一个已经精确评估过的 ΔCPI**（保护、解耦、剪枝、掩盖检测），它就输，因为它和 CPI 出自同一个模型。
2. **当前瓶颈**：MSCS 记录的是"时间花在哪一级、哪一类"，DSE 需要的是"各级还剩多少能力、具体改哪个资源"。并且 MSCS 只通过 Base 影响 CPI，而 Base 可以由 CPI 反算，所以它在搜索中没有提供 scalar 之外的信息。
3. 方向是对的，信号是弱的：基于压力水平的信号（0.58）好于基于变化量的（0.43），掩盖也真实存在。缺的是表示粒度。

## 6. 与 MSCS 无关、可直接用的改进

- 回收：按省面积从大到小评估，遇到第一个可接受的就停（决策不变，每步约省 1/3 query）。
- 平台期：评估 scalar 前 4 个单参数的两两组合（约 4 次 query，78% 的情况能超过最好的单参数移动）。
- BO 中拟合 −log Base 并乘回已知的 W_min（只用 CPI，待验证）。

## 7. 尚未尝试的方向

- **以分量定义目标**（例如均衡设计或最坏情况鲁棒性，在 6 个 Google benchmark 上做未见 workload 评估）：g 对分量是非线性的，scalar 无法表达。
- **各级能力余量**：如果 MSCS 或 gem5 stall 计数能导出每一级的剩余能力，吞吐量 ≈ min（各级能力）就是一个强非线性结构，可以直接用于掩盖检测和 composite BO。
- **按资源拆分 BP**（ROB、IQ、LSQ、FU、cache）：使 MSCS 具备 ArchExplorer 式的可操作性。
- 训练端价值在 DSE 中的体现：标签预算 vs gem5 验证的真实前沿（不使用分量本身）。
